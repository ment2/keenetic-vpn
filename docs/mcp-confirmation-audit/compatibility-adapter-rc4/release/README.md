## New compatibility path

* `adapter.mjs`: separate owner portal and authenticated MCP interfaces. The owner portal binds a specific authenticated client via an independently paired registry, prepares an immutable task using the pinned RC2 validation, displays its exact content and obtains the owner's explicit approval of the pairing. The normal host tool call must present the same arguments and non-secret `request_ref`; the verified client identity must match. Neither a model-supplied `confirmed` nor possession of a reference authorizes a request. Explicit false fails closed. No method is exposed to the model that obtains owner consent or signs an arbitrary task. The real host request is a prerequisite; this candidate does not attest that ChatGPT showed a separate confirmation dialog.
* `read-recovery.mjs`: independently scoped adapter function for the existing authenticated `GET /v1/requests/:key`; fixed HTTPS origin, no redirects, no mutations, no automatic resend. A safe `get_operation_status`/`ha_get_operation_status` returns the verified job identifier for existing job-result tooling and never submits a job. Unknown outcomes remain unknown. No direct `/v1/jobs` fallback.
* `recovery-store.mjs`: owner-local Node SQLite metadata store. A unique request reference and upstream request key are committed before dispatch, alongside target, HMAC-separated identity digests, time and conservative state. No task, proof, raw principal, token, or private key is persisted. Reopening allows only read-only recovery, never a repeated mutation; pending private keys remain memory-only and expire. Hard record limit; no automatic deletion of unresolved records. Private regular-file and private directory checks, full synchronous transactions. Provision the private ancestor directories and stable HMAC key independently through owner-managed secret storage. No HMAC key is generated or transferred by this package. The Node 22 SQLite implementation is an isolated reference; a distributed/Worker deployment requires equivalent independently tested durable single-writer semantics. A safe retention/export/terminal-record cleanup workflow remains required before a long-running production release.

## Supported candidate mutations

| Target | MCP tools | Notes |
| --- | --- | --- |
| Keenetic | `write_file`, `exec_command`, `queue_router_task` | Legacy alias supported for exec/write only; migrate its read_file callers to the unchanged named read tool. No widening of path/content bounds. |
| HA | `ha_write_file`, `ha_exec_command` | HA add-on scope remains unchanged. |

Named write options follow the pinned server defaults; unsupported mode/timeout is rejected rather than silently lost. Exec timeout is preserved. New descriptors require a reference and the actual configured OAuth security scheme; preserve destructive annotations and define a read-only status tool/output schema. Existing read tools, queue result tools and authentication routes must remain unchanged in a future integration. The adapter exposes no owner tool or proof field. Existing clients lacking a reference must fail closed; this is a migration, not transparent backward compatibility.

The `verifyClient`, `verifyOwner`, `resolvePairedClient` functions are **required trusted integration points**, not implemented authentication or proof of host consent. They must use actual server-validated identity (issuer, audience/resource, subject, client id, stable authenticated binding, current scopes/expiry/revocation), not user-supplied claims, arbitrary HTTP headers, tool inputs or a shared Bearer token presented as a per-client identity. Owner pairing must be independent of model messages. An owner action is obtained only in the authenticated portal; the portal's explicit boolean is not a host approval indicator. The regular MCP dispatch route must be inaccessible except through its own authenticating ingress, and owner routes must be separately authenticated and protected from CSRF. Do not construct a proxy that resubmits operations denied by the host. A tool call admitted by the host and a separate owner approval are distinct gates.

## Real compatibility gap discovered from exact archived inputs

* The native accepted Keenetic baseline ment2/keenetic-control@c422f98ec4ec9b4626603a893de877ff74e161ef, `worker/src/worker.mjs` blob `7d31e40f47ee87cfa93010d59ba38fea15c58497`, uses a common admin Bearer at `/mcp`. A common token cannot prove the identity of a particular remote client or session; do not bind based on a caller-supplied header. Its current working tools expose the older `confirmed` schema. The distinct host/Site authentication boundary must be established through supported integration, or a separately reviewed client-specific OAuth flow introduced in staging. No scope or endpoint is guessed.
* Exact archived HA OAuth primary from 2026-11-27 (SHA256 `2972f8fa590b4f8ce15e9221abc34ca527cd703fd002bbf07fda657a530ba9b8`), which was used as the RC3 baseline: `OAuthStore.validate` checks a live access/grant/epoch/resource/scope and returns only `valid:true`. `authenticateMcp` then translates the validated token to the common `CONTROL_ADMIN_TOKEN` and drops its client identity. Grant records have a server-generated stable grant ID and `client_id`, resource, scope and epoch, but no independently authenticated end-user subject field. Preserve a minimal verified grant binding in private server-side context *before* translation; derive subject from the actual owner authentication boundary, not from invented grant fields. The internal validation route must stay inaccessible externally. No token, grant ID or private session values should be returned to the model. The exact deployed version has not been attested. Do not deploy the archived primary or this adapter merely because the source was inspected.
* Editable app packages for both currently connected remote plugins contain only app/manifest references, not the actual running server implementation. Updating their manifest cannot implement the required transport or identity binding. No production app was modified, no old blocked live source operation retried, no new tool permissions or authentication scopes requested. A supported owner-controlled remote server release path with verified current source, verified authentication and isolated namespace is a prerequisite for wiring the candidate into the live ingress. The synthetic marker test does not grant authorization for real device operations.
