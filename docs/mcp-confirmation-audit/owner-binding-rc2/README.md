## Design and trust boundary

The existing owner and remote-enable/scope checks and MCP destructive annotations remain. `confirmed` is still strictly boolean when present; `owner_admin` is still a server permission, not a platform approval. RC2 removes the model-facing `approval_id` and does not accept old bearer grants. The pending approval is retained by the server, not sent in a conversation.

1. An authenticated trusted client prepares the exact normalized operation and creates a fresh nonextractable P-256 private key. The client sends the request UUID, public key and signature of target, registration phase, UUID and normalized task digest to `/v1/operation-pending`. The existing bridge authenticates the request before routing it. The server verifies key possession and returns a fresh random challenge. It retains only the task digest, public key, fingerprint, challenge, revision, expiry and state; no plaintext operation content in the pending table. The digest includes the existing normalized task and write-content SHA-256. The table is bounded at 100 rows; expiry is 120 seconds from registration, not extended by approval. Expired records are pruned on registration, not by a guaranteed wall-clock background task.
2. The independently authenticated owner surface matches the fingerprint against the intended trusted client channel and presents the exact task. An explicit approval action invokes `/v1/owner/approve-operation` with that task, request key, fingerprint, challenge and literal `confirmed: true`. Both pre-existing owner credentials remain required. Owner pairing must be independent of data asserted by a chat/model; the ephemeral key alone proves possession, not a named ChatGPT account or session identity. `owner-transport.mjs` provides an injected transport interface, not a deployed identity provider.
3. Following the genuine host-authorized invocation, the trusted client signs a domain-separated consumption message for the exact target, request UUID, digest and fresh server challenge. It supplies the existing `Idempotency-Key` and `X-Operation-Proof` **as transport headers**, not a model argument or chat message. The coordinator verifies the signature and then atomically rechecks the immutable fields, current revision, time and state in the same SQLite transaction as job insertion. Concurrent calls can create at most one job; an identical signed duplicate within the validity window may return the same job. The client adapter itself never automatically repeats a send. No old grant, boolean, missing/wrong proof, stale challenge, changed task or changed policy may authorize a new mutation. A nonmutating call cannot reserve an already registered mutation request key.
4. `/v1/owner/revoke-operation` requires both owner credentials and matching request UUID, fingerprint and challenge. The transaction moves pending/approved to revoked. It races with enqueue atomically: a successful revoke prevents the job from being queued; if consumed first, revoke returns 409. It is not a cancellation of an existing queued/running job. A lost approval response allows an explicit revoke without submission. No retry or alternate channel after denial/uncertainty. The client-side adapter refuses a revoke once it has begun submission; the separately authenticated server owner endpoint remains able to race until the queue transaction consumes the approval.

The proof is not a host authorization attestation. A trusted transport must only sign/send in a real host-authorized invocation and keep private key/proof in that transport, not expose the transport as a model-callable tool. A stolen proof can be replayed for the **same** pending request, with no second insertion; do not log it or transfer it outside the intended transport. Existing authenticated direct job-result reads are unchanged. This design does not establish a unique persistent principal behind a shared bearer or independently attest the user action at the owner credential boundary. Existing production adapters have not been integrated. For HA, OAuth authorization of `/mcp` is unchanged; pending registration uses the existing authenticated `/v1` REST boundary, so an OAuth-only client must use a legitimately authenticated trusted transport and must not receive admin/policy secrets in ChatGPT. Never call REST as a fallback for a host denial.
