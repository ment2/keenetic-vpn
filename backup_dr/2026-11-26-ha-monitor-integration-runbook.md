## Behavior

The 80 s local child watchdog is not a remotely submitted HA exec timeout: those remain <=45 s. Public health preflight stays in existing child; only exact preflight-unavailable markers with return code 4 permit a degraded retry on the next normal cycle and only if there is no journal. All other ambiguous errors without a journal stop the monitor. Startup and post-child checks use ha_receipt_retry.deliver_pending, with agent.lock held during delivery. result_ready gets receipt-only POST with existing authenticated API and same lease/result; public preflight is also required before each receipt submission. No ordinary child invocation in a cycle that begins with pending result. No new claim on a cycle with receipt recovery. Claimed/invalid journal, lock contention, bad ACK, non-transient errors or exhausted retry stop the monitor. No automatic deletion except matching ACK and unchanged journal. Retry delays 1,3 s; 3 attempts total per explicit recovery cycle. Ordinary child still performs its initial result delivery; retry attempts are additional to that original attempt. Explicit operator start after exhaustion starts a new bounded cycle. No auto-reconciliation, policy change, token rotation, new job, or auto-start after add-on restart.

Existing API preflight timeout 12 s and request timeout 20 s are socket-level bounds, not guaranteed absolute end-to-end DNS/slow-read deadlines; the new receipt path runs in the monitor process, not under its child watchdog. Nominal receipt budget up to 3*(12+20)+4 = 100 s, not a hard deadline. Stop is cooperative, not an interrupt of in-flight receipt. Must validate actual latency and shutdown behavior on HA before production promotion. Lock serialization assumes cooperative processes and trusted local root; no claim of defending against malicious root or noncooperating writers.
