# Backup DR pending envelope and configuration generations — offline candidate

Baseline: ment2/keenetic-vpn commit d9c58776a4bf272ecfdc1d6aa342829249e990a0. Scope: offline only. No HA, Keenetic or Cloudflare calls, changes, transfers, keys or live archives. Existing Backup DR v3.5 release ZIP is unchanged and does not contain this candidate.

## Crash consistency

New `pending_envelope.py` stores a versioned canonical header (configuration digest, source fingerprint, ciphertext SHA-256 and length), ciphertext and domain-separated HMAC-SHA256 together. Group binding uses the existing per-group key; config digest binds membership. Header is authenticated, not independently encrypted; source fingerprint and config digest are metadata in a private local file. No plaintext archive is staged. Enforce existing bounded ciphertext size, header size, regular file, ownership, private permissions and link count; validate format and MAC before sending. Write to an exclusive fixed `.tmp`, flush/fsync, rename to final name and fsync directory before any send. Recover a complete authenticated staging file; incomplete staging, conflicting names, wrong key/config, mismatched state, corrupt envelope and ambiguous legacy artifacts fail closed and remain available for review. A complete final file without pending state reconstructs its matching pending metadata; a previously accepted matching digest and source fingerprint allows cleanup without resending. Legacy `pending.gcm` with matching existing metadata remains deliverable. Receipt commit remains before removal. No source fingerprint or preflight before retry of a valid saved archive. Current code assumes cooperating processes holding state locks, a trusted private state directory, and filesystem durability semantics. No physical power-cut or MIPS memory/IO validation performed.

## Membership change and history

`group_registry.py` maintains role-separated authenticated configuration maps with active and retired membership digests. Normal sender tick and receiver initialization reject unapproved configuration changes. Initial migration adopts only the reviewed current legacy plan; sender refuses unidentified generation directories. Receiver legacy archive membership remains checked by manifest and unknown historical directories are not automatically removed. The registry does not prove which plan a legacy receiver previously used. `approve_change(...,coordinated=True)` is a local maintenance helper, not a network protocol or automated migration. It requires the caller to stop and fence both roles, review old/new plans, drain all pending sender work, and hold service/registry/state locks as applicable. Never call it on a live receiver, even if a direct library consumer omitted its service lock. A single role cannot prove the other is stopped. Two local registry updates are not a distributed atomic transaction: if one fails, keep both services stopped, retain old/new plans and registry evidence, and resolve or roll back explicitly; do not auto-start with divergent generations. No production migration command is activated. Membership changes are tracked without changing per-group encryption keys; old archive bytes and filenames remain intact, and restores use their original authenticated manifest. Retention verifies current membership, excludes historical membership, skips removed groups, and conservatively skips pruning a reactivated retired generation. Historical files still consume quota; they may remain indefinitely and block new backup capacity until an approved historical retention/export policy is defined. Group status currently summarizes active group directories; global quota includes retired directories. No automatic purge of retired data or pending envelopes. Do not downgrade runtime binaries with a pending envelope; drain/verify under the new version first, preserve all state, and recheck both roles before rollback. Historical key recovery and owner escrow remain separate gates.
