# Keenetic Backup DR v3.3 — offline installation and recovery gate

Base: 6284f8f6ebe381bbc2173574df176df4de99082f. Candidate only. Live v2 synthetic byte fixture previously passed on both devices; v3.1/v3.3 group acceptance on physical devices has not passed. The earlier Keenetic write was blocked; no repeat or alternative deployment channel is attempted. No real backup, key provisioning, production service, firewall, cron or HA panel change in this stage.

## Storage controls
- Global hard limit 2 GiB of logical regular-file bytes under dedicated private archive root, including inactive groups, unrecognized files and leftover temporary files. 5 GiB minimum free SSD capacity. Per-group allocation must sum to no more than global limit. Private root, same filesystem, no symbolic links or special files. Global flock serializes cooperating store and retention operations. Identical retransmission can return the existing authenticated receipt at full quota. No eviction on quota exhaustion; alert and retain data. External uncoordinated writers, filesystem metadata overhead and storage exhaustion by other apps are outside the hard logical quota; free-space check is not a reservation.
- Retention: 30 days, retain at least two newest cryptographically verified generations per active group. No deletion of inactive group archives, corrupt data or unknown files. Scheduled retention integration remains a deployment task. Group/key migration requires review; old archives consume global space.

## Backup groups
See group-policy-v3.3.json. Quotas are proposed defaults, adjustable before installation. Exact per-file allowlist is not inferred from aggregate sizes. Owner-reviewed list is mandatory; no broad collection of credential files or implicit session export. SQLite online backup with quick_check, bounded memory; no raw WAL/SHM copies. Large files >4 MiB require a separate reviewed recovery strategy. Package inventory must be generated locally without package credentials; rebuild matching MIPS packages on replacement Keenetic, not on Raspberry Pi ARM. Native router configuration outside /opt needs a separately approved device-native export. HA integration on Raspberry Pi is a separate backup domain.

## Recovery key
Use independent offline RSA-3072 recovery key on owner-controlled encrypted storage; keep the private key off Keenetic, HA, GitHub, library and backup SSD. Two protected offline copies, preferably separate physical locations. Pin public PEM SHA-256 out-of-band before wrapping the randomly generated 32-byte master. The escrow envelope contains only ciphertext, recipient fingerprint and master identity. Preserve those expected identities independently; verify offline unwrap and restore of a synthetic archive before first production backup. Keep old escrow and key IDs until all corresponding archives are retired. Do not generate or copy actual keys via chat or MCP. Never put runtime master or recovery private key in source package. Separate local operational master on sender and receiver under private directories (0600), provision only via owner-reviewed local procedure with verified recipient public keys; no plaintext transport. Real escrow not yet created or validated on owner storage. RSA envelope primitive tested with synthetic keys in RAM.

## Installation acceptance order
1. Verify bundle SHA-256 manifest against independently trusted GitHub commit; run `python3 -m unittest discover -v` on an isolated test host. `python3 install_gate.py --bundle .` performs only offline package/policy validation. No installation action.
2. Review exact per-group allowlist and exclusions on source; run preflight with approved config, verify disk and memory margins, package manifest and native config export. Empty/missing group is a blocker. Do not proceed if tool denies deployment.
3. Owner-approved local installation plan: versioned private directories, nonoverwriting staging, verify hashes; no modifying existing VPN, bot or HA workloads. Persistent receiver and scheduling require explicit service lifecycle design and rollback, initial synthetic fixture on both devices, plus manifest/SQLite isolated restoration, quota rejection, retention and restart tests. No automatic startup until all pass. All HA MCP command timeouts <=45s; bounded long-running process only after confirmed readiness.
4. Provision and verify real recovery escrow offline. First actual backup only after exact scope and authorization, verify receipt and isolated recovery. Restore does not activate files; review metadata and architecture before manual production cutover. Monitor stale heartbeat, group age, failed backup, quota and reserve. No real production backup in this stage.

## Failure and rollback
Stop only the new candidate service and timer (once installed); retain encrypted archives, state and escrow. Never delete existing archives or overwrite production source as a rollback. Original Xray, bot, HA and existing MCP continue untouched. An unknown command outcome must be reconciled, not replayed. A queue reset cancels all queued HA jobs; use saved local recovery tool only if necessary.
