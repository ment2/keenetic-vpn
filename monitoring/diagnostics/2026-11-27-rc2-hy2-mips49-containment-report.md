## Full-system lab
New source monitoring/lab/mixed_rc2/mips49_containment.c and .github/workflows/rc2-mips49-containment.yml. Disposable QEMU Malta 4KEc, 256 MB, 1 CPU, no NIC/network backend; loopback only. Pinned Debian linux-image-4.9.0-13-4kc-malta 4.9.228-1 mipsel package SHA256 9a5dff9c498bf5736ca9f97cbb005b4b60bd139aa0f30f5bab9feca783907d9b; extracted kernel SHA256 20f5380e02f2e40d4495fd61a854e5867f5ccdf95c8c1fd3d53fe27e8be1797f. No production firewall and no guest firewall modifications; only bring guest loopback up. Uses real kernel sockets, not mocks. Parent prepares two synthetic UDP receiver sockets and one connected UDP sender, forks a child, closes own sender copy; child closes receivers, drops supplementary groups/UID/GID, sets no_new_privs and holds on pipes so parent can independently compare socket inode in /proc/PID/fd and /proc/net/udp and verify effective UID and capabilities. Parent receives exact known bytes and checks no forbidden bytes within bounded local observation window. Child reaped and fd path gone. No external traffic possible by construction.

Negative control: unprivileged process UID 65534 CapEff=0 can use sendto to send data to a different destination even on connected UDP socket. This proves UID drop/no_new_privs alone does not guarantee no-leak. Positive limited containment: arch-pinned seccomp allowlist read/write/exit/exit_group only, all other syscalls EPERM. A single preconnected UDP fd can transmit allowed bytes via write; sendto alternate destination, connect alternate destination and new socket all return EPERM; allowed write still succeeds and forbidden receiver has no bytes. This is a deliberately constrained synthetic program, NOT a general sandbox for Xray or Go runtimes. `nnp_proc=0` in 4.9 output means the status parser did not find a positive NoNewPrivs field; child explicitly checks successful PR_SET_NO_NEW_PRIVS before sending proof. No claim independent proc NNP witness. No independent AF_PACKET capture, arbitrary destination coverage, TCP/IPv6/DNS policy, adversarial privileged root, or actual Xray socket factory tested in this experiment. /proc inode correlation is a per-process, live gated socket witness, not complete system-wide QUIC session ownership. Exact no-leak scope is the synthetic forbidden loopback receiver for tested operations and interval, not production no-leak.

## Remaining gates
1. Provider: obtain documented unknown option name/semantics from NerpVPN; do not expose credentials or assume mportHopInt. Keep Hysteria2 rows unsupported until verified.
2. Process isolation: Xray creates its own sockets; applying strict synthetic filter unchanged would break Xray. Need independently verifiable destination-specific containment for dynamic TCP/UDP/DNS sockets. Linux 4.9 seccomp sees syscall numbers/arguments but cannot safely inspect pointed-to sockaddr memory as a general destination ACL. No general production containment proven. A network namespace with a controlled path or an independently enforcing socket broker would need separate feasibility and acceptance; do not deploy, modify firewall, or assume vendor kernel supports either. Consider separate monitoring worker on a suitably isolated Linux host only as a distinct architecture with separate path/egress semantics, not an equivalent Keenetic acceptance.
3. Device remains unchanged. Prior native config test passed, but installed binary differs from official reference, actual Hysteria2 handshake and source route no-leak unverified. Separate authorization needed for any physical capability test/installation, and actual provider tunnel run only after both option and containment gates.
